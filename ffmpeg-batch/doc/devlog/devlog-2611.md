## 2. 问题根因与技术判断

### [4] 未应用目录直接扫描导致服务退出

旧前端只向 `/api/scan` 发送空请求，没有提交输入框的新目录；后端调用 `void manager.scan()` 且不附带 `.catch()`。当管理器尚未初始化项目时，异步函数开始处的 `throw` 变为未处理的 Promise rejection；在 Node 默认未处理拒绝策略下，可能使服务器进程退出。

修复后扫描请求携带 `source/output`，后端按需先进行同步路径校验与配置，并给异步扫描显式兜底。非法目录返回 HTTP 400，服务继续运行；在 API 无项目时也会立即返回可理解的错误。

### [5] 历史批次混用

旧设计只有单一 `manager.project` 和上次目录配置，没有可供切换的会话索引。新设计增加 `manager-sessions.json`（运行时本地索引），按源/输出目录对绑定各自状态文件，重新打开旧任务不丢失旧扫描与转码记录。每个新会话默认建议新的同级输出目录，避免复用相同目标文件路径产生覆盖风险。

### [3] 转码参数硬编码引发验收误判

旧版无条件追加 `-c:v libx265` 和 `-vf scale=宽:高`，且 `checkOutput()` 固定要求 HEVC；仅修改命令生成会使无编码器、H.264、AV1 等合法模板被误判为失败。现将模板规范化、目标尺寸计算、命令参数与已知编码器验收联动。新任务默认不传上述可选参数；已有任务迁移时保留旧式 `libx265 + fit720`，避免无意更改历史处理意图。

### [1][2][6] 界面限制

旧主题 CSS 同时包含变量与大量硬编码深色背景，仅修改 :root 变量不足以完成亮色主题；增量提供明确的 light 覆盖。旧目录树只统计筛选列表的文件数，不含子树状态分类；现在对完整任务树做递归汇总，并把统计挂回当前筛选树。原程序没有媒体流接口，使用任意文件路径访问会有本地文件泄露风险；新增受任务目录及扫描清单双重约束的媒体服务，支持 HTTP Range 和双播放器。

- 模板变更时重新生成目标尺寸与具体命令；已完成项目改模板标记目标冲突，不覆盖旧输出。

### 7.1 根因与技术结论

1. **分数模式不存在**：此前 `workflow.js` 仅支持 none/percent/exact/fit720，百分比依赖普通浮点计算。分数例如 `2/3` 不应先化成循环小数；采用正整数分子和分母、`BigInt` 约分及整数乘除，从输入直到最终尺寸取整都不使用分数的浮点近似。
2. **短边模式不存在**：此前仅能按最大边界适配 720p 或原尺寸百分比，无法指定任意目标短边。现在以 `min(width,height)` 确认短边，长边按 `原长边 × N / 原短边` 精确计算。
3. **独立模板缺乏视觉线索**：旧 `t.override` 已被持久化，但未在文件行显示。添加「独立参数」标记，并与当前处理状态并存。
4. **任务运行状态全局化**：此前 `Manager` 只持有一个活动 `project/activity/runningChild`，切换时会通过 `openProject` 替换项目并重载状态文件，容易干扰仍在运行的异步回调。现在用 `Manager` 协调器维护各 `SessionWorker` 实例，每个任务独立持有项目状态、进度、扫描、验收、队列、FFmpeg 子进程与暂停/停止标志。切换仅更新 UI 选中的会话，不重新加载已在运行的实例。
5. **转码中数字未显示**：后端 `counts.running` 早已存在，处理队列仅缺少相应指标方框及 DOM 更新。现补在「转码完成」之后。
6. **用户配置留在程序目录并曾被 Git 跟踪**：旧 `.manager-config.json` 位于项目根目录，任务索引也位于根目录；现迁入 `.data/` 并加入 Git 忽略，移除仓库中旧版配置文件。程序会在启动时创建 `.data` 并迁移仍保留在磁盘上的旧文件，已存在的新位置文件不会被覆盖。

### 7.2 实际修改

**计算和模板**

- `normalizeFraction` 只接受正整数分子/分母，拒绝零、非法输入和超长数值；使用最大公因数约分，`720/1080` 与 `2/3` 规范化为相同模板值。
- `roundEvenRatio` 用整数四舍五入到最近偶数，确保 `1920×1080 × 2/3 = 1280×720`。只有最终目标像素发生取整，不通过 Number 保存循环小数。
- `shortEdge` 模式可在批量与单文件模板中设置 N；横屏 `1920×1080 → 1280×720`、竖屏 `1080×1920 → 720×1280`。短边保留用户指定整数 N，长边按精确分数取最接近偶数；最终尺寸限制为合理范围。
- 模板校验、单视频覆盖、生成的 `-vf scale=宽:高`、已有输出冲突判定与验收预期目标尺寸保持一致。
- 两种模式均配有表单示例和取整说明；不改变旧 `fit720` 或既有模板的字段语义。

**并行会话与安全**

- `SessionWorker` 按每任务独立执行扫描/转码/验收，管理层仅负责建立、切换与列举任务；运行中创建、切换和启动其他任务不会更改原任务执行上下文。
- API 中对异步操作的回调固定绑定当次的 worker，而不在执行中回头引用当前 UI 选中的全局项目；暂停、停止、重试、验收也只调用所选任务。
- 多任务不允许共用同一物理输出目录；比较真实路径，阻止符号链接别名造成跨任务文件覆盖。
- 原视频/结果视频预览链接包含所属会话 ID；在其他任务选中后继续 Seek/Range，不会切换到其他任务的同名文件。

**前端与数据文件**

- 任务侧栏运行期间始终允许新建、选择其他任务，显示各任务运行状态及正在转码的视频数量。
- 目录树文件行新增「独立参数」视觉标记，与转码状态并列；处理队列「转码中」紧随「转码完成」，窄屏布局保持二者同行。
- 运行目录 `ffmpeg-batch/.data/` 在启动时创建，`/.data/` 已写入 `ffmpeg-batch/.gitignore`；`.manager-config.json` 和 `.manager-sessions.json` 从原目录迁入该目录，配置不会再被 Git 跟踪。
- 每个任务原有的 `.h265-720p-state.json` 继续存放于该任务的输出目录，不迁移也不丢失。
- `test/run-tests.js` 为测试创建和清理独立的本地配置目录，避免 `npm test` 更改真实用户运行数据。
- 更新 `ffmpeg-batch/README.md`，记录新增表单、并行语义、迁移边界与测试方式。

**1. 新建任务仍展示历史任务**

## Q1-D — 2026-11-08：双视频播放到末尾后无法从头重播

### 问题现象与根因

- 用户反馈：`双视频对比`窗口中，视频已经播放到末尾，再点击底栏统一播放按钮 `▶`，两个播放器仍停留在结束位置。
- 原 `public/compare-sync.js` 的 `toggleBoth()` 在视频 `paused/ended` 时调用 `playBoth()`；但 `playBoth()` 始终先执行 `align(safeTime(reference))`，因此仍以源视频接近末尾的 `currentTime` 对齐两个播放器，然后直接调用 `video.play()`。
- 已结束的 `HTMLMediaElement` 并不保证在这种同步控制流程下自动回到起点，导致统一播放无效。既有的 `commonTime` 还将时间限制在共同片长末尾之前，进一步放大了这个行为问题。

### 实际修复

- 增加 `reachedEnd(reference)`：任一视频 `ended` 为真，或播放时间已接近双方可播放的共同末尾时，判断为重播场景。
- `playBoth()` 首先识别重播场景，**强制分别设置两个播放器的 `currentTime = 0`**，确保进入播放阶段前双方都从头开始；随后并行调用两侧 `play()`。
- `place(video, time, force)` 支持强制设置时间，即使播放器报告的时间已经非常接近 0，也不会因为浮动容差而跳过解除 `ended` 状态所需的定位。
- 没有到达末尾时，仍按照先前逻辑从当前时间同步续播；原有暂停/前后跳转、键盘快捷键、媒体 Range 和项目切换行为不变。
- 支持两段视频时长不一致的场景：只要一侧结束，再按统一播放便将两侧重置到开始位置。

### 测试及验收

- `test/compare-sync.test.js` 新增三项回归：双方都已结束时自动从 0 秒重播；只有较短视频结束时两侧一起重播；结束时间附近但 `ended` 标记尚未更新时也重播，同时验证中途暂停仍从暂停点继续。
- 测试中的 `VideoMock` 增加更接近浏览器的 `ended` 状态规则：当尚未重置进度时拒绝播放，成功归零后允许恢复。
- `test/browser-ui.test.js` 增加 **Chromium 页面真实点击底栏 `▶`** 的结束态重播测试：模拟两个 `HTMLMediaElement` 到达末尾，断言双方进度为 0、双方播放状态恢复、按钮显示 `⏸`。
- GitHub Actions：[42413617117](https://github.com/Ltre/Ltre.tool/actions/runs/42413617117)；`npm run check:syntax` 和 `npm test` **38 项通过、0 失败、0 跳过**，包括原有的真实 FFmpeg/ffprobe 验收与多任务回归。

## Q1-E — 2026-11-08：短边等值跳过缩放、标记输出体积增长

### 需求与实现顺序

1. 先修正短边缩放的目标尺寸计算和 FFmpeg 命令生成，确保两者一致，避免省略滤镜后验收失败。
2. 在已有 `bytes`（源文件）和 `outputBytes`（验收通过的输出）基础上统一计算体积差异；不增加重复持久化字段，保证既有历史完成任务自动兼容。
3. 再扩展队列统计、目录树醒目标记/筛选、文件详情和 CSV/JSON/命令导出；最后追加单元、HTTP/真实 FFmpeg 集成、历史恢复和 Chromium 页面测试。

### 问题根因

- 原 `workflow.calculateTarget()` 的 `shortEdge` 分支不区分「源短边本来已经等于 N」，总是计算长边并按偶数取整；对奇数宽高，可能连本不需缩放的分辨率都改变。
- 原 `workflow.commandArgs()` 只判断 `scaleMode !== 'none'`，不管输入/目标大小是否相同，始终添加 `-vf scale=宽:高`，产生无意义的滤镜处理。
- 源文件字节数与输出字节数已被扫描与验收流程记录，但缺少「输出更大」的统一判定、可见标记、筛选和报告字段。

### 具体修改

- `workflow.js`：若原短边 `Math.min(width,height) === shortEdge`，直接返回原始宽高，且执行参数中不加入 `-vf scale`。非等值时仍按照原来的长边等比例及偶数取整规则，视频编码、质量、音频复制、`+faststart` 均保持原样。
- `server.js`：恢复历史任务时仅重新计算**尚未完成**视频的预设尺寸和命令，不修改已完成视频的实际命令记录。增加 `outputSizeComparison()`：只有 `status === 'done'` 且源/输出均有有效正整数字节数时，`outputLarger = outputBytes > bytes`，`sizeDeltaBytes = outputBytes - bytes`；否则标记 false、差值 null。
- 接口 `/api/status`、JSON 导出：按快照派生每条任务的 `outputLarger` / `sizeDeltaBytes` 和总计 `outputLargerCount`；无需修改历史状态数据文件。CSV 报告增加 `outputLarger`、`sizeDeltaBytes` 两列；命令列表对输出增大的文件加上文字标识。
- `public/app.js`、`index.html`、`workspace.css`：目录树已完成文件行显示「↑ 输出比原文件大」提醒，文件详情显示体积增减字节数及百分比，新增「输出比原文件大」筛选；处理队列原有体积摘要增加增大文件个数，不改变已有五项状态指标和任务隔离逻辑。表单帮助文字与 README 同步更新。
