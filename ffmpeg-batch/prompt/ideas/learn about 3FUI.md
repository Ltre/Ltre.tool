# 3FUI 有什么可以借鉴的


我查了 3FUI（FFmpegFreeUI） v6 的官方项目说明和功能资料。结合你正在开发的 ffmpeg-batch，我认为有不少值得借鉴的东西，而且有些可以进一步做得比 3FUI 更方便。

最值得学习的不是 3FUI 提供了多少 FFmpeg 参数，而是它围绕「预设方案 → 批量入队 → 执行监控 → 结果评估」形成的一套工作流。

3FUI 已提供参数预设、独立任务配置、批量队列、预计剩余时间与输出大小、质量评测、性能监控，以及外部程序调用等能力。

GitHub+1

下面我区分它已有的实践和针对你工具提出的扩展想法。
一、我认为最有价值的 12 个方向
优先级	功能方向	对 ffmpeg-batch 的实际价值
高	先试转，再批量执行	避免几十 GB 视频转完才发现体积变大或画质不满意
高	批量选择视频并套用模板	一次选中几十个视频，统一指定局部模板
高	智能扫描与跳过规则	自动识别不值得重新压缩的视频，减少浪费
高	动态预计时间和输出体积	清楚知道还要多久、可能节省多少空间
高	同一任务内并行转码	多个小视频同时转码，提高设备利用率
中	批量管理操作	对筛选结果统一设置、暂停、重试、排除
中	编码器能力自动检测	自动识别可用的软件/硬件编码器，避免无效参数
中	模板效果统计与对比	知道哪套模板压缩得小、速度快、质量合适
中	智能失败处理	根据错误类型定位问题，并允许批量重试
中	转码后质量抽查	不必逐一打开视频，可快速比较关键画面
低	任务优先级与调度策略	紧急视频插队、夜间运行、按预计耗时排序
低	远程投递与自动化规则	其他设备提交任务，甚至自动处理指定目录

其中前三项对你现在的项目提升尤其明显。

2. 智能扫描：不值得转码的视频直接排除
你目前已经有 ffprobe 扫描、分辨率判断、体积统计以及筛选功能。

这些信息可以组合成转码前的智能筛选。

例如一个源目录有 300 个视频，扫描后区分为：
批量扫描结果 · 示例

182

54

39

需人工检查
25


不是自动认定某种编码一定需要或不需要转码，而是按照用户设置的规则分类。

可配置规则包括：源编码格式、分辨率、码率、文件大小、时长、文件名，以及是否已经存在验收通过的输出。

它也可以与 Q1-F 的多模板功能联动。例如高码率 H.264 用 H.265 模板，低码率 H.265 不处理，特殊文件单独采用保守模板。

这会显著减少重复劳动。

4. 预计剩余时间、文件大小与空间需求
这是 3FUI 很实用的功能。它能够显示预计剩余时间和预计最终体积。

GitHub

你的工具目前已经能显示进度和转码速度，可在此基础上扩展：
- 当前文件预计完成时间
- 整个任务队列预计完成时间
- 当前输出文件预计体积
- 本轮可能节省或增加的磁盘空间
- 当前磁盘剩余容量是否足够
尤其是最后一点。批量处理几十 GB 视频时，即使压缩后的总量更小，中途仍需要为临时输出文件预留额外空间。
5. 自适应并行转码，而不是固定同时执行多个视频
3FUI 的批量队列和性能监控值得借鉴。

GitHub

你目前支持不同任务会话并行，但同一任务内部仍主要逐个转码。

下一步可以实现整个应用的统一调度器，让它根据任务、编码器和硬件资源决定并发度。

例如：
- 软件 H.265 编码消耗大量 CPU 时，可能只需同时处理 1～2 个。
- 短小视频较多时，可以尝试提高并发度。
- NVENC、QSV 等硬件编码需要结合 GPU 编码负载及硬件并发限制。
- 大文件读写密集时，还需要考虑磁盘吞吐量。
这里真正应该优化的是单位时间完成的视频总量，而不是进程数量。 最好通过实测吞吐量动态调整，而不是盲目增加并行任务。
6. 让多模板不仅能复用，还能比较效率
3FUI 的预设体系支持保存和分享编码方案。

GitHub
 我认为你可以进一步为每个模板长期累计统计数据。
例如：
模板	已完成	平均体积变化	平均转码速度
H.265 CRF 23	125	'-38%	1.3×
H.265 CRF 27	86	'-51%	1.6×
H.264 CRF 22	70	'-19%	3.2×

表内为示例数据，不代表任何模板的实际性能。用户一眼就能知道哪套模板在自己的视频素材和设备上表现更好，而不只是凭经验反复调参。

统计时最好还能按输入编码、分辨率和设备分组，避免不同素材之间的平均数产生误导。
三、值得进一步发散的两个功能
转码后自动识别“不划算的结果”。 你在 Q1-E 已经实现了输出变大的标记。接下来可以让用户设定处理规则：输出比原视频大超过指定比例时，保留源文件、单独归类，或者等待用户决定是否换模板重试。不能仅根据体积变大就认定转码失败，因为有时保留更高质量本身就是目标。

可重复执行的转码方案包。 3FUI 已支持从外部程序传入预设和任务，也支持远程调用及任务事件订阅。

GitHub
 你的 Node.js Web 管理器可以更自然地扩展成可分享的 JSON 方案，包含模板、筛选规则、输出目录命名、验收条件和失败处理策略。下次处理类似素材时，一次导入即可复用整套流程。
四、我建议的发展顺序

第一阶段：减少人工操作

完成 Q1-F 的多模板机制，同时增加多选视频、批量套用参数、按条件自动分配模板。这一阶段操作效率提升最明显。




第二阶段：减少无效转码

加入片段试转、体积预估、智能跳过规则及批量验收，提高一次转码成功率。




第三阶段：提高实际吞吐量

增加资源监控和自适应并发调度，逐步优化长时间、大批量转码。




第四阶段：自动化与智能化

模板效果统计、目录自动处理、远程投递、可选的 AI 参数辅助等。



我觉得你的工具没必要完全照搬 3FUI 那种专业参数面板。3FUI 本身也明确定位于懂一定编码知识的进阶用户。

GitHub

你的优势恰恰在于目录树、批量管理、历史任务恢复、体积变化分析和双视频对比已经有比较完整的基础。

如果最终能实现这样的流程：

扫描一批视频 → 自动分类 → 批量匹配模板 → 少量试转 → 确认后批量执行 → 自动验收 → 只查看异常结果

那么面对几百个视频，用户可能只需要操作几次，而不是逐个设置、逐个检查。这会比单纯增加更多 FFmpeg 编码选项更有价值。
